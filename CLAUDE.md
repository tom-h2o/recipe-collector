# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev          # Vite dev server (frontend only; API routes need Vercel CLI to work locally)
npm run build        # tsc -b && vite build (must pass before committing)
npm run lint         # ESLint
npm run test         # Vitest run (single pass)
npm run test:watch   # Vitest watch mode
npm run test:ui      # Vitest with browser UI
npm run test:e2e     # Playwright e2e tests (tests/e2e/); starts its own dev server (E2E_PORT to move it off 5173)
npm run db:migrate   # npx supabase db push — applies any new /supabase/migrations/ files to the remote DB
```

To run a single test file: `npx vitest run src/lib/recipeUtils.test.ts`

## Architecture Overview

**Deployment:** Vercel. The frontend is a Vite/React SPA; the backend is Vercel Serverless Functions in `/api/`. Each endpoint is its own function file — Vercel routes `/api/<name>` to `api/<name>.ts` automatically. The SPA catch-all (`/(.*) → /index.html`) is in `vercel.json`.

**Database:** Supabase (Postgres + RLS). Schema is in `/supabase/migrations/`, numbered and applied in order — the count is not written here because it went stale (this line said 38 at 61). Tables: `recipes`, `recipe_images`, `recipe_ratings`, `recipe_translations`, `recipe_shares`, `meal_plan`, `shopping_list`, `pantry_items`, `settings`, `account_links`, `contacts`, `collections`, `recipe_collections`, `url_cache`, `ai_cache`, `gemini_logs`, `shortcut_keys`, `recipe_imports`, and storage for recipe photos. `recipes.embedding` is a pgvector column (768-dim `gemini-embedding-2`); `recipes.search_vector` is a `tsvector` for server-side full-text search.

**AI:** Claude (via `@anthropic-ai/sdk`) is the main provider since migration 0069, with Google Gemini (via `@google/genai`) as the automatic backup and for the 768-dim recipe embeddings, which Anthropic does not offer. Every AI endpoint returns JSON. Which model a task runs on is a model id: `claude-*` goes to Claude, anything else to Gemini, and a Claude failure of any kind falls back to a Gemini model inside the same call (see "Claude is the main provider" under Key Patterns). The models are stored on the global `settings` row (`id = 1`) and chosen by the admin for everyone; the temperature unit is per user, on the user's own row. Prompts live in `api/_lib/prompts.ts` only (per-user prompt overrides were removed in 0043).

### Frontend (`/src/`)

- `App.tsx` — root component: initialises all hooks, wires up views, handles routing for the `/recipe/:id` public share URL
- `types.ts` — all shared TypeScript interfaces (`Recipe`, `Ingredient`, `Nutrition`, `MealPlan`, `ShoppingItem`, `PantryItem`, `AppSettings`, `RecipeTranslation`, `RecipeShare`, `Contact`, `Collection`, `RecipeCollection`)
- `components/ui/` — shadcn/ui primitives (built on `@base-ui/react`); add new primitives here via the shadcn CLI, don't hand-author
- `lib/constants.ts` — `MODELS`, `FILTERS`, `AVAILABLE_TAGS`, `MEAL_TYPES`, `LANGUAGES` (en/de/fr/es — Polish was removed in migration 0062), `SORT_OPTIONS`, `PAGE_SIZE` (24)
- `lib/recipeUtils.ts` — `parseIngredients()` (defensive: handles both `Ingredient[]` and legacy `string[]`, though the DB now enforces `Ingredient[]` via a check constraint), `scaleAmount()`, `recipeToIngredientText()`
- `lib/temperatureUtils.ts` — parses °C/°F (and written-out "degrees") in recipe text and converts to the user's preferred unit at display time
- `lib/supabase.ts` — singleton Supabase browser client
- `lib/api.ts` — `apiFetch(url, options)`: attaches the Supabase session Bearer token to every API request
- `lib/sentry.ts` — Sentry frontend init (no-ops if `VITE_SENTRY_DSN` is unset)
- `store/recipeStore.ts` — Zustand store holding recipe list state (`recipes`, `processingIds`, pagination, in-flight polling intervals) and the actual `fetchRecipes`/`loadMore`/`saveRecipe`/`updateRecipe`/`deleteRecipe`/`toggleFavourite` implementations; `useRecipes` (below) is a thin hook wrapper around it

**Hooks** (each owns its own Supabase queries and state, except `useRecipes`):
- `useRecipes` — thin wrapper around `store/recipeStore.ts` (Zustand); exposes paginated recipe list (PAGE_SIZE=24), polling for AI processing completion (`processingIds` set), `saveRecipe`/`updateRecipe`/`deleteRecipe`/`toggleFavourite`
- `useMealPlans`, `useShoppingList`, `useSettings` — self-explanatory
- `useAuth` — Supabase Auth: password + magic link. Returns `user`, `loading`, `isPasswordRecovery`, `sendPasswordReset`, `updatePassword`, `resendConfirmation`, `signOut`
- `useRecipeShares` — inbox (pending shares), contacts for autocomplete, `sendShare`/`acceptShare`/`rejectShare`
- `useCollections` — manages `collections` and `recipe_collections` tables; CRUD for user-created recipe collections; takes `userId` param
- `useTranslationCache` — pre-fetches translations for every recipe that has a `preferred_language` set; uses a `fetchedIds` ref to prevent re-querying on unrelated recipe list updates (e.g., toggling a favourite)
- `useDarkMode` — syncs with `prefers-color-scheme` and persists in `localStorage`
- `useRecipeImports` — what the iPhone Shortcut sent and the person has not seen (`recipe_imports` with no `seen_at`): new recipe ids, still-processing, failed; polls while something is processing, refetches on `visibilitychange`, `markSeen(recipeId)`, `dismiss(importId)`
- `useShortcutKey` — status / create / revoke of the person's Shortcut key via `api/account.ts`; holds a freshly made key until Settings closes
- `useUsage` — fetches today's Gemini call count for the logged-in user from `gemini_logs`; used by `SettingsPanel` to show the daily usage meter

**Components** (one per feature, all in `/src/components/`):
- `ErrorBoundary` — standard React error boundary; wraps top-level app subtrees
- `PublicRecipe` — printable standalone recipe view rendered at the `/recipe/:id` public share URL (no auth required); print-optimised via Tailwind `print:` utilities
- `AuthGate` — wraps the whole app; shows login UI if unauthenticated; handles "claim existing recipes" for pre-auth data. Includes password, magic link, forgot password, and set-new-password (recovery) flows. All errors shown inline (never toast-only).
- `Layout` — header, nav tabs (Vault / Meal Planner / Shopping / Inbox), action buttons. Inbox tab shows orange badge when pending shares exist. Suggest button always rendered (removing it conditionally caused navbar height jitter).
- `RecipeVault` — grid with search, filter chips, sort, infinite scroll ("Load more")
- `RecipeCard` — individual card with processing spinner badge; shows translated title/description if `recipeLanguages[recipe.id]` is set
- `RecipeDetail` — full-screen drawer: scaling, translation, cook mode entry, edit/delete/share/send
- `RecipeForm` — add/edit dialog; URL extraction and photo upload flows
- `CookMode` — fullscreen step-by-step mode with ingredient side panel
- `MealPlanner` — 7-day calendar
- `ShoppingList` — shopping + pantry tabs
- `SettingsPanel` — temperature unit, and the AI models: editable by the admin (for everyone), a read-only "model per task" list for anyone else; Usage Logs tab shows daily usage meter (progress bar + per-endpoint breakdown) and recent AI call history
- `SuggestModal` — ingredient-based AI recipe suggestion
- `SendRecipeModal` — send a recipe to another user by email; autocompletes from known contacts
- `RecipeInbox` — displays pending received recipes with Accept / Decline actions
- `UserMenu` — profile dropdown: signed-in provider, change password, sign out
- `GeminiLogs` — recent AI call history (endpoint, model, status, latency, expandable input/output)
- `ImportBanner` — top of the vault: "N new recipes from your photos · Show", "Reading … from your photos", and each failure with its reason and a dismiss
- `ShortcutSettings` — Settings → General → iPhone Shortcut: make, replace or remove the key (shown once), **Add to Shortcuts** once the admin has shared the Shortcut (admin: paste its iCloud link), and the build steps as fallback
- `AdminPanel` — admin-only dashboard: global stats, and server-side-paginated Users/Recipes/AI Logs tabs (25 rows/page, fetched from `GET /api/account?tab=...`)

### API (`/api/`)

Each handler is a standard Vercel serverless function: `export default async function handler(req: VercelRequest, res: VercelResponse)`. All handlers follow the same pattern: `setCorsHeaders` → OPTIONS guard → method guard → Zod validation → cache check → rate limit check → read settings → call Gemini → return JSON.

**Shared helpers in `/api/_lib/`:**
- `cors.ts` — `setCorsHeaders(res)`, reads `ALLOWED_ORIGIN` env var
- `supabase.ts` — `getServerSupabase()` (service key), `getSettings(supabase, userId?)` (models from the global `id=1` row, temperature unit from the user's own row), `saveModelConfig()` (writes the global row; admin endpoint only), `resolveApiKey()`, `getUserId(authHeader: string | undefined)` — takes the raw Authorization header string, not a VercelRequest
- `gemini.ts` — despite the name, the provider-neutral entry point: `generateJson()` and `generateFromParts()` (photos/PDFs) route by model id, retry, fall back across models and providers, log every call to `gemini_logs` (table name kept) and capture errors to Sentry; also `getGeminiClient()`
- `claude.ts` — the Claude half: `askClaude()` (one request), `claudeFormat()` / `toJsonSchema()` (Gemini response schema → structured-output JSON Schema), `toClaudeContent()` (Gemini parts → image/document blocks), `getClaudeClient()` from `ANTHROPIC_API_KEY`
- `photoExtraction.ts` — `extractRecipeFromImages()`: the photo branch of `extract.ts` and the Shortcut import read pictures through this one function (same prompt, `photo`/`extract` task by kind, one log row); also the `LANGUAGE_*` rules every extraction prompt shares
- `enrich.ts` — `tagRecipe()` / `estimateNutrition()` (+ `DailyLimitError`): the cores of `/api/tag` and `/api/nutrition`, shared with the Shortcut import, which saves and enriches on the server
- `shortcutImport.ts` — the iPhone Shortcut import (see Key Patterns); `imageBytes.ts` — format sniffing, pixel size and lenient base64 splitting for what a Shortcut sends
- `prompts.ts` — default prompt templates (one export per endpoint); `getSettings()` returns the user's override if they've saved one in Settings, else these defaults
- `schemas.ts` — Zod schemas for all request bodies
- `sentry.ts` — server-side Sentry init, `captureException()`
- `cache.ts` — helpers for both the `url_cache` table (extract endpoint, 7-day TTL) and the `ai_cache` table (other AI results)
- `rateLimit.ts` — `checkRateLimit(supabase, userId)` counts today's `gemini_logs` rows; `DAILY_LIMIT = 100` exported (imported by `useUsage.ts` — single source of truth); returns 429 when exceeded. Rows whose endpoint is in `NON_AI_ENDPOINTS` (`shared/usage.ts`: `find-image`, `health-check`) do not count
- `systemCheck.ts` — the admin System tab: `configReport()` (env vars as set/missing, never values), `reasoningReport()`, and `runLiveCheck()` (database, schema version, Realtime, auth, storage, Unsplash, a probe of every Gemini model and the embedding model). See "System check" under Key Patterns

**Endpoints (all at `api/<name>.ts`, 11 total):**
- `extract.ts` — fetch URL → cheerio scrape → Gemini → JSON recipe (7-day URL cache); also handles photo (`imageBase64`), PDF (`pdfBase64`) and pasted text (`text`) extraction, and, with `?via=shortcut`, the iPhone Shortcut import (key auth, saves the recipe)
- `tag.ts` — generate tags + a 768-dim `gemini-embedding-2` text embedding for a recipe, stored in `recipes.embedding`
- `nutrition.ts` — generate nutrition data for a recipe
- `suggest.ts` — suggest recipes from available ingredients; embeds the ingredient list and calls the `match_recipes` pgvector RPC (cosine similarity, threshold 0.1) first, falls back to in-memory string scoring if no vector matches
- `shopping.ts` — generate shopping list from meal plan recipes
- `scale.ts` — AI-assisted recipe scaling
- `translate.ts` — translate recipe to another language (cached in `recipe_translations` table)
- `find-image.ts` — find a suitable image URL via Unsplash
- `share.ts` — recipe sharing: `send` / `accept` / `reject` actions
- `share-preview.ts` — server-rendered Open Graph tags for a public share link. Reached **only** by preview crawlers: `vercel.json` rewrites `/r/*` here on a user-agent `has` condition, and everyone else falls through to the SPA, so a fault here cannot stop a person opening a link. Fails to a 302 at the real page rather than an error.
- `account.ts` — GET: admin dashboard, paginated per tab (`?tab=overview|users|recipes|logs&page=&pageSize=`, max page size 100), plus `?tab=health` (System tab: configuration and reasoning, no outside calls); POST `?action=health-check`: admin, runs the live checks; POST `?action=models`: admin, sets the AI models for everyone (Zod: only ids in `OFFERED_MODELS`, only known tasks); POST `?action=shortcut-url`: admin, the shared Shortcut's iCloud link (iCloud Shortcut links only); any signed-in user, own key only: GET `?tab=shortcut-key`, POST `?action=shortcut-key` (make/replace, returns the key once), POST `?action=shortcut-key-revoke` — handled first, so they can never fall through to DELETE; DELETE: delete own or (admin) any user account

## Environment Variables

Copy `.env.example` to `.env.local`. Required:
- `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` — Supabase project
- `SUPABASE_SERVICE_KEY` — service role key (API functions only, never browser)
- `ANTHROPIC_API_KEY` — the Claude key, for the main provider. A Claude Max plan includes monthly API credit once a Claude Console organisation is linked to it. Without the key nothing breaks: every task runs on its Gemini fallback, and the System tab shows the Claude models as skipped.
- `GEMINI_API_KEY_1` — the Gemini API key, for the backup and for embeddings. **Within Gemini there is no failover**; Claude is now the second provider that the paragraph below says was missing. `resolveApiKey()` reads this (falling back to `GEMINI_API_KEY`) and nothing else; an earlier version of this file described `GEMINI_API_KEY_2` as an optional second key, which was never wired to anything. A single project is therefore a single point of failure: on 2026-09-15 three calls failed with `403 PERMISSION_DENIED` "Your project has been denied access" and every AI feature was down until it cleared. A second key from the *same* Google Cloud project would not help — a project-level denial applies to all its keys — so real failover means a second project, with its own billing.

Optional: `VITE_SENTRY_DSN`, `SENTRY_DSN`, `VITE_APP_ENV`, `ALLOWED_ORIGIN`, `VITE_ADMIN_EMAIL` (email address granted admin panel access), `UNSPLASH_ACCESS_KEY`

GitHub Actions secret needed for DB migrations: `SUPABASE_DB_URL` (Postgres connection string from Supabase dashboard → Project Settings → Database → URI).

## Key Patterns

- **`ingredients` field:** stored as `Ingredient[]` (objects with `amount`, `name`, `details`); a DB check constraint (`chk_ingredients_format`, migration 0036) enforces this on all rows and legacy `string[]` data was migrated. Frontend code still uses `parseIngredients()` from `recipeUtils.ts` defensively before rendering or processing ingredients.
- **Processing state: Realtime first, poll as the net.** After saving a recipe, `recipeStore.startPolling()` opens a `postgres_changes` subscription on that row *and* starts a 5s poll; whichever sees `tags.length > 0 && nutrition != null` first calls the shared `finish()`, which tears down both. The `processingIds` set drives spinner badges on cards; the 30s timeout still applies. **Do not delete the poll.** `postgres_changes` only fires for tables in the `supabase_realtime` publication (migration 0059), and a subscription to an unpublished table connects, reports `SUBSCRIBED`, then stays silent — indistinguishable from "still processing" until the timeout. The same is true of a blocked websocket or a lost event, so removing the poll would trade a 2s delay for a 30s hang. Realtime is covered by `src/store/recipeStore.test.ts`, which fakes the channel and delivers events by hand.
- **Pagination & search:** `fetchRecipes()` resets to page 0; `loadMore()` appends. Search runs server-side via Postgres full-text search (`recipes.search_vector` tsvector column, queried with `.textSearch()`); tag/sort/filter also run at the DB level, not client-side.
- **Auth + RLS:** The browser client uses the user session (RLS enforced). API functions use `SUPABASE_SERVICE_KEY` (bypasses RLS). Recipes with `user_id = null` are visible to all authenticated users (legacy data).
- **Per-recipe language:** `recipes.preferred_language` stores the last-used display language per recipe. Written via `updateRecipe()` when the user switches language in RecipeDetail — **and only once a translation for that language exists.**
- **Translating must never trap the reader, and never starts by itself.** Three rules in `RecipeDetail`, each from a reported hang. (1) **Opening a recipe never calls `/api/translate`.** The effect that resolves the display language reads memory, then the `recipe_translations` row, and if there is neither it puts the recipe back on its original (`onLanguageChange(null)`) instead of making one. It used to translate on open, so a recipe whose display language had nothing stored spent an AI call every time it was opened. (2) **The display language is saved after the translation succeeds, not before.** `handleTranslate` keeps the language being made in `pendingLanguage` and calls `onLanguageChange` only in the success path; saving it first is what created the state in (1) whenever a translation failed, was refused by the guard, or was deleted. (3) **No chip is ever disabled by a running translation.** Choosing any language, or the original, aborts the request (`AbortController`) and switches; the picker used to be `disabled` for the whole call, which can run for a minute or more, and that read as the app having hung. The server may still finish and store an abandoned translation; that only makes the language "already translated" later. `tests/e2e/translationFlow.spec.ts` recreates all three against a backend that remembers rows and saves, and fails on the old behaviour. The picker also offers **Delete this translation** while a stored translation is on screen; the `⋯` menu keeps one entry per stored row.
- **Per-user settings:** the `settings` table has one row per user, keyed by `user_id`. Until migration 0051 this never worked: 0003's `check (id = 1)` outlived 0038's move to a sequence, so *every* insert failed — including the one an upsert performs, because Postgres evaluates CHECK constraints on the proposed tuple before looking for the ON CONFLICT arbiter. Do not add a CHECK constraint on `settings.id` or on model ids.
- **Settings shows what each model id actually ran as.** `useModelResolution` reads the viewer's own `gemini_logs` rows and reports the latest `model_version` per configured id, with "not used yet" where there is no evidence — never an inferred answer. This exists because an alias hides the real model and Google moves them silently (`gemini-flash-latest` went 3.7 → 3.8 unannounced, then stayed on the 3.x tier when Gemini 4 shipped under new names).
- **The AI models are the admin's choice, for everyone (migration 0068).** They used to be per user, so anyone could put every task on Frontier, which has no free allowance: on a key without billing every one of their calls failed. Now `getSettings()` takes `gemini_model` and `task_models` from the global row (`id = 1`) **only**; a user's own row contributes `temperature_unit` and nothing else, and model columns left on it are ignored (kept, not dropped, so an older build still open in a browser does not break). The one write path is `POST /api/account?action=models` (admin, service key) — RLS already keeps every user off row 1 (`settings_update`, 0020; pgTAP checks it), so hiding the controls in `SettingsPanel` is a courtesy, not the guard. Users read row 1 directly under `settings_select` to show which model each task runs on. `useSettings.saveSettings` writes only `{ user_id, temperature_unit }` to the user's row and posts models only when they changed. `system_health()` reports only row 1's models, so the System tab does not probe ids nothing runs. Covered by `api/accountModels.test.ts`, `src/hooks/useSettings.test.ts`, `tests/e2e/adminModels.spec.ts` and three pgTAP cases.
- **Per-task models:** `settings.task_models` (jsonb, migration 0052) maps an `AiTask` to a model id; a missing key falls back to `gemini_model`. Endpoints must resolve via `modelFor(settings, task)` from `api/_lib/supabase.ts` — reading `settings.gemini_model` directly still works but silently ignores the per-task choice, so `tests/unit/modelFor.test.ts` fails any endpoint that does. The task list is declared in both `src/types.ts` and `api/_lib/supabase.ts` and the same test asserts they match.
- **The global settings row:** the `settings` table has one row per user, keyed by `user_id`, plus the global row `id=1, user_id=null`. The `id` column uses a sequence starting at 2. Since 0068 the global row is not a fallback but the only source of the models (previous bullet but one); `GLOBAL_SETTINGS_ID` names it in `api/_lib/supabase.ts` and `src/hooks/useSettings.ts`. Frontend upserts its own row on `user_id` conflict.
- **Auth required on AI endpoints:** every AI endpoint returns 401 if `getUserId()` resolves to `null` (no/invalid Bearer token) before doing any work — there is no legitimate unauthenticated caller since the frontend is fully auth-gated. Rate limiting then calls `checkRateLimit(supabase, userId)` AFTER the cache check (cached responses bypass the limit). Returns 429 at 100 calls/day. Count derived from `gemini_logs` rows for the current UTC day.
- **The Supabase CLI version is pinned in two places and they must agree:** `supabase/setup-cli` in the `rls` job, and the `supabase` devDependency that `npx supabase` resolves in `migrate-production`. CLI 3.0 renamed `[inbucket]` to `[local_smtp]` in `config.toml`, and 2.x rejects the new key — so a split across majors breaks one job or the other, on whichever PR happens to run next. Never use `version: latest` here. `tests/unit/supabaseCliVersion.test.ts` fails on drift between the two pins or a config key that does not match.
- **RLS has its own test suite:** `supabase/tests/rls.test.sql` (pgTAP), run by `supabase test db` against a local Postgres with every migration applied — the `rls` CI job does this. It covers what nothing else can: unlinked isolation, that a *pending* invitation grants nothing, that an accepted link is symmetric, that reading is not writing, per-person rating visibility, that settings are not shared by a link, and that disconnecting revokes access. Needs Docker, so it does not run in the main `validate` job. Add a case here whenever a policy changes.
- **Testing RLS requires a real session, not the service key.** `SUPABASE_SERVICE_KEY` bypasses RLS entirely, so any check made with it is blind to exactly the policies it is meant to verify — a broken policy looks identical to a working one. To exercise a policy as a given user, impersonate them in the SQL editor:
  ```sql
  begin;
  select set_config('request.jwt.claims',
    '{"sub":"<user-uuid>","role":"authenticated"}', true);
  set local role authenticated;
  select count(*) from public.recipes;   -- the query under test
  rollback;
  ```
  Used to confirm account linking on 2026-09-05: the requester saw 11 recipes (own 7 + linked 4), proving `recipes_select` and `linked_user_ids()` widen the read as intended.
- **Ratings are per person, not per recipe:** `recipe_ratings (recipe_id, user_id, rating)` is the source of truth, and its primary key is what makes rating a linked account's recipe safe — a write adds the viewer's row rather than overwriting the owner's. `recipes.rating` survives as a **trigger-maintained cache of the owner's rating only** (`sync_owner_rating`, migration 0053), because the "Highest rated" sort runs server-side inside the paginated query in `recipeStore.ts` and moving it to a join would change that query's shape and the owner filter layered on it. Never write `recipes.rating` directly.
- **Writes RLS refuses are silent:** an update whose row the policy excludes matches zero rows and PostgREST returns **no error**. `updateRecipe` in `recipeStore.ts` therefore asks for the affected rows (`.select('id')`) and throws when none came back — without that, the optimistic local merge painted changes that were never written. Any new write path against another user's rows needs the same treatment.
- **Glass, the sliding tab pill and touch feedback live in `index.css`, driven by tokens and two data attributes.** `.glass` (tab bars, dropdown menus) and `.glass-bar` (header, denser at 0.82 because it carries the name and the buttons) take their colour from `--glass-surface` / `--glass-alpha` and their blur from `--glass-blur`; `.glass-menu` raises the alpha because a menu carries text over arbitrary content; `.glass-control` is the round button on a card's photo and `.glass-dark` the smoked close button, for a white icon over a picture of any brightness. Dialogs stay opaque on purpose. **Glass needs thickness, not just transparency**: on a page that is mostly cream, a translucent cream surface reads as a pale sticker, so `.glass` also carries a rim of light along the top (`--glass-rim`), a sheen (`--glass-sheen`), a falling-off at the bottom (`--glass-shade`) and two outer shadows, one for contact and one for height. The fade under the phone tab bar is short and light for the same reason: a deep fade hides exactly the content the glass is there to show through. **Three fallbacks, all by changing those tokens**: no `backdrop-filter` support → alpha 1 (`@supports not`); `prefers-reduced-transparency` → alpha 1 and no blur (both rules name `[class*='glass']` and are `!important`, because the variants set their own alpha and would otherwise stay translucent); `prefers-reduced-motion` → no scale, no spring, the pill jumps, **but the fade stays**, because it is the only acknowledgement of a tap. A surface that hard-codes its own alpha escapes all three; `tests/unit/glassFallbacks.test.ts` checks that. Colour tokens here follow the house rule (bare channels, alpha in its own token) or `tests/unit/theme.test.ts` fails. **The tab pill is one element per bar**, positioned by `usePillPosition` from the tab marked `aria-current="page"` — measured, because the labels differ in width — and it is not animated until the first measurement has painted, or it would slide in from the left on every load. **Touch feedback is `data-pressed` / `data-released`, set by `src/lib/pressFeedback.ts`, not `:active` with a transition.** Nearly every control carries a Tailwind transition utility, and whichever one it is replaces `transition-property` wholesale, so a press written as a transition is soft on some controls and instant on others; a keyframe animation is untouched, and CSS cannot start one on release by itself. Everything tappable fades; `button`s also scale to 95%; `.bg-sk-primary` darkens instead of fading (fading the one solid thing on screen reads as disabled); a `data-pressable="surface"` (recipe cards) fades but never shrinks. A plain `div` with an `onClick` needs `data-pressable` to take part. `tests/e2e/liquidGlass.spec.ts` covers the bar, the pill, the pressed states and the two fallbacks a browser can be switched into. **Screenshots of glass from this container must be taken at `deviceScaleFactor: 1`.** Its Chromium renders through SwiftShader, and at 2x a `backdrop-filter` blurs only the upper part of its box: text under the lower part stays sharp. That is the renderer, not the CSS — a bare page with one blurred box shows it — but it makes glass look broken in exactly the picture meant to judge it.
- **Nothing tappable may sit under the iPhone's status bar or home indicator.** `index.html` sets `viewport-fit=cover`, so on an iPhone the page runs up behind the clock and the Dynamic Island and down behind the home indicator; taps there go to iOS, not the page. The edit form and the delete confirmation still open as siblings of the drawer and have not been checked for the same faults.

- **Every AI response is shape-constrained:** each endpoint passes a `responseSchema` from `api/_lib/responseSchemas.ts`. `responseMimeType: 'application/json'` only *asks* for JSON — the model can still emit something unparseable, which caused four of the five failures ever recorded in `gemini_logs` (and a second billed call each time, to the JSON repair path, which then also failed). The Zod schemas in `schemas.ts` still validate the result: Gemini constrains structure, Zod enforces what its subset cannot express (a two-letter code, a uuid, a non-empty string). The two are hand-kept in sync and `tests/unit/responseSchemas.test.ts` fails on drift or on an endpoint that sends an unconstrained request.
- **Gemini logging:** every `generateJson()` call inserts **exactly one** row into `gemini_logs`, regardless of retries. This is load-bearing: `checkRateLimit` derives the 100/day allowance by counting rows, so a row per attempt would charge a user two or three for one action (the mistake that once let `find-image` consume the AI budget). `attempts` on the row records how many model calls it really took. Visible in `GeminiLogs` and the admin dashboard.
- **Provider errors are never passed to the user verbatim:** `describeGeminiError()` in `api/_lib/gemini.ts` maps a Gemini failure to a user-facing message and an HTTP status, and every AI endpoint's catch block uses it. The frontend renders the response's `error` field as-is, and endpoints used to return `err.message` — which for a Gemini failure is the provider's JSON envelope, so a cook saw `{"error":{"code":403,…,"status":"PERMISSION_DENIED"}}` and could reasonably read it as a fault in their recipe. A configuration or quota fault returns **503**, not 500, because nothing about the request was wrong. Our *own* wording (Zod messages about the model's output) is deliberately preserved — only something shaped like the provider envelope is replaced. The raw error still goes to `gemini_logs` and Sentry; that is how the 403 outage was diagnosed two months later. `api/_lib/geminiErrors.test.ts` fails any endpoint that reverts to passing `err.message` through.
- **Reasoning is off where there is nothing to reason about.** `generateJson()` takes `thinking` (default **on**, so this is opt-out per endpoint). Translation runs with it lowered (`thinkingFor('translate')`, see the next bullet but one) — as far as the model allows, which differs by family (next bullet but two). Gemini 4 thinks by default and it is paid for twice: in latency (a successful translate is recorded at 124s) and in the chance the reasoning leaks into the answer — a stored title came back as ``Vegan Chocolate Mousse``` Wait! I almost output extra text and markdown!…``. Rewriting given text into a given shape has nothing to reason about. It is deliberately *not* applied to every endpoint: extraction from messy HTML may genuinely benefit. The repair retry inherits the same setting, or the second billed call would quietly cost the latency the first one avoided. `api/_lib/gemini.test.ts` covers all three.
- **A translation is checked before it is stored.** `findTranslationFault()` in `api/_lib/translationGuard.ts` compares the model's answer with the text that was sent, and `api/translate.ts` passes it to `generateJson()` as `validate`. The response schema fixes the *shape* only: the leaked-reasoning title above was a valid string in the right field, and once upserted it was served from `recipe_translations` on every later open — the only way out was deleting it by hand. The rules are deliberately coarse (a code fence the source does not have, a multi-line or wildly overlong title, a different ingredient count, instructions several times longer or cut to a fraction, **a different number of steps**), so each describes something no honest translation does; it is not a quality check. **Steps travel as an array, in both directions.** `instructions` is one string everywhere else in the app and a step is only whatever sits between two line breaks (`splitSteps()`, the same rule `RecipeDetail`, `CookMode`, the print sheet and the public page split on). Sent to the model as that one string, a translation came back with steps 1 to 4 run together into a single point — every word right, the structure gone, and cook mode left with one screen for the whole dish. `api/translate.ts` now sends `splitSteps(instructions)` as a JSON array and states the count, `translationResponseSchema` declares `instructions` as an ARRAY of STRING, and `translationResultSchema` joins the entries back with `\n` (flattening a line break *inside* an entry, which would otherwise split one step in two). Do not turn it back into a STRING. **The second ask happens inside `generateJson`, not in the endpoint**, because `checkRateLimit` counts `gemini_logs` rows: one call, one row, `attempts: 2`. A second refusal throws `TranslationRejectedError`, whose message is our own wording and therefore passes through `describeGeminiError`. Nothing re-checks rows already in the table.
- **Reasoning per task is decided in one place, and every call records what happened.** `REASONING_OFF_TASKS` in `api/_lib/supabase.ts` (today: translate, tag, nutrition) is read through `thinkingFor(task)`, and every `generateJson` call passes `thinking: thinkingFor('<its task>')` — `tests/unit/reasoningConfig.test.ts` fails a hard-coded `thinking: false` or a task that is not the endpoint's `modelFor` task, because the admin System tab displays this list and would otherwise disagree with what runs. Each `gemini_logs` row carries `thinking` (migration 0067): `on` (the default, asked for), `off`, `minimal`, `low`, or `refused` (every lower setting refused, ran at the default). The column has no CHECK constraint, so these values were added without a migration; the column's own SQL comment still lists the first three. Rows are written through `insertGeminiLog()`, which, if the insert is refused for the `thinking` column (the minutes after a deploy before the migration job runs), writes the row again without it: a lost row is a free call, since the daily allowance counts rows. The admin logs tab and the user's own Usage Logs read the column the same forgiving way.
- **System check (admin → System).** Configuration and reasoning load with the tab and call nothing outside the app; the live checks cost a call per model (Claude and Gemini), an embedding and an Unsplash search, so they run only on **Run check** (`POST /api/account?action=health-check`). Every probe lowers reasoning the way a real task does (Gemini: `withReducedReasoning`, from the first step each time; Claude: low effort, asked directly with no fallback, and shown as skipped — with nothing logged — when `ANTHROPIC_API_KEY` is not set), which is also the test of which setting the model accepts, and writes one `gemini_logs` row with endpoint `health-check`, which `NON_AI_ENDPOINTS` keeps out of the daily allowance. Probed: every id in `OFFERED_MODELS` (a server copy of `MODEL_OPTIONS`' ids, kept equal by `reasoningConfig.test.ts`) plus any other id a user has configured, read by `system_health()`. That function (migration 0067, `security definer` only to read `supabase_migrations`, service role only) also reports Postgres and pgvector versions, whether `recipes` is in the Realtime publication, and the newest applied migration, which the tab compares with **`EXPECTED_SCHEMA` in `api/_lib/systemCheck.ts` — bump it with every new migration**; `api/_lib/systemCheck.test.ts` fails when a newer file exists. The probe wording is for the admin and deliberately more specific than `describeGeminiError()`, which speaks to a cook. Configuration is reported by variable name as set or missing, never a value (also tested). `tests/e2e/systemCheck.spec.ts` holds that opening the tab sends no POST.
- **"Reasoning off" means different things per model family, and a refusal steps down.** Only Gemini 2.5 can switch reasoning off (`thinkingBudget: 0`). From Gemini 3 on the numeric budget is legacy and reasoning can only be *lowered*, with `thinkingLevel`: the admin System tab's first real run showed `gemini-3.5-flash-lite` answering a zero budget with a bare **400 "Request contains an invalid argument."** — no mention of thinking, so the old detector (a 400 *mentioning* thinking) let it through and every tag, nutrition and translation call on Lite failed, Lite being the recommended model for tag and nutrition. `reducedReasoningSteps(model)` in `api/_lib/gemini.ts` now returns, most reduced first: Gemini 2.5 → budget 0; Gemini 4, `gemini-3.8-*` and Pro models → `LOW` (Google's table offers no `minimal` there); any other id → `MINIMAL`, then `LOW`. `withReducedReasoning()` sends each in turn, takes **any 400** as a refusal of that setting (`refusesReasoningSetting`), and finally sends no reasoning setting at all (`refused`). A request wrong for some other reason therefore costs one fast failing call per remaining step and then fails as before. What each model accepted is remembered per warm instance, so later calls go straight to it; the System tab probe starts afresh (`fresh: true`). Tagging and nutrition run lowered too — both run after every save and are what the card's spinner waits for; nutrition is a trade (an estimate either way, possibly a little less steady) and is the one to take out of `REASONING_OFF_TASKS` if values drift. Google's levels per model are documented at aistudio.google.com/docs/thinking; `minimal` is not guaranteed to be no reasoning at all.
- **Transient Gemini errors are retried:** `callWithRetry` in `api/_lib/gemini.ts` retries 429/500/502/503/504 and `UNAVAILABLE`/`RESOURCE_EXHAUSTED`/`INTERNAL` with exponential backoff plus jitter, and stops early rather than starting a retry that would outlast the serverless execution ceiling. **The deadline must stay larger than a single call takes.** It was 7000ms, from a guess about the ceiling that `gemini_logs` disproves — a translate call has succeeded at 124s — and since `extract` takes 10-53s its first failure always blew the budget, so retrying never once fired on the endpoint people notice. It is now 110s, and the check budgets for the retry costing roughly what the failed attempt cost rather than treating it as free. Permanent errors (400, 404 for a retired model id, auth) are never retried — they fail identically every time. **Photo and PDF extraction used to be the exception**: they called `generateContent` directly, so an overloaded model failed a photo on the first try while every text task waited and tried again. They now go through `generateFromParts()`, and `tests/unit/responseSchemas.test.ts` fails if `extract.ts` calls `generateContent` directly again.
- **A model that cannot serve is replaced by the other free model, inside the same call.** "Gemini is down" is usually *one* model: each has its own capacity and its own free quota, and the System tab has shown Standard answering 503 while Lite was fine. `withModelFallback()` in `api/_lib/gemini.ts` runs the chosen model (with its retries) and, if it still fails with something `modelCannotServe()` covers — the transient set, which includes 429 for a used-up quota, or 404 — runs `fallbackModelFor(model)` once: Standard ↔ Lite, anything else → Standard, **never Frontier** (no free allowance). A 403 is deliberately excluded: a blocked project is blocked for every model, which only a second provider would fix. Both runs share one deadline and the fallback starts only if it is likely to finish. `generateJson` and `generateFromParts` both use it; the log row is still one row, with `attempts` counting both models' calls and `model` naming **the model that answered**, so `useModelResolution` keeps pairing `model` with its `model_version`. The repair and re-ask go to the model that answered, with the reasoning setting that model accepted. The two ids are copied rather than imported from `OFFERED_MODELS` (every endpoint test mocks `supabase.ts`); `gemini.test.ts` holds them equal.
- **Admin dashboard pagination:** `api/account.ts` never fetches an unbounded table. Users/Recipes/Logs tabs each query only their requested page; per-user `recipe_count`/`ai_call_count` on the Users tab are `head: true` counts scoped to just that page's user ids (not a full-table scan). Emails for Recipes/Logs rows are resolved per-row via `auth.admin.getUserById()`, bounded by page size. The model-usage breakdown in `getStats()` is counted by the `gemini_model_usage()` function (migration 0066), callable by the service key only. It used to select every `gemini_logs` row and tally in JavaScript, which was worse than unbounded: **the API returns at most 1000 rows per request, silently** (`max_rows`), so past a thousand logged calls the chart counted an arbitrary thousand while the head-only total beside it was right. Any query that fetches rows in order to count them has this problem — use `head: true` or an RPC. A failing RPC costs the chart, not the page, which also covers the minutes after a deploy before the migration job has run. Covered by `tests/unit/adminStats.test.ts` and three pgTAP cases.
- **Release notes ("What's new"):** entries live in `src/lib/changelog.ts`, newest first, so a note ships in the same commit as the change it describes. `id` is a `YYYY-MM-DD` date compared as a plain string — never reuse or re-order ids. "Seen" is the newest acknowledged id in `localStorage` (per device, deliberately: no migration, and no write on every view). A first-ever visitor is shown nothing but has the marker written immediately, or there would be nothing to compare against when the next release ships and they would never see that one either. Add an entry whenever a change is user-visible.
- **Cook mode timer:** `parseDurations()` in `src/lib/parseDurations.ts` pulls durations out of a step's text (en/de/pl — the languages present in the vault) and cook mode offers them as chips. The unit word is mandatory in the regex so an oven temperature never becomes a timer. `useCookTimer` counts down from an **absolute deadline**, never by decrementing per tick: browsers throttle intervals in background tabs, so a tick-based timer silently loses minutes exactly when a locked phone is relied on. The timer deliberately survives step navigation.
- **Printing / "Save as PDF":** `RecipePrintSheet` renders a separate, print-only page portalled to `<body>`, and `@media print` in `index.css` hides everything else with one selector (`body > *:not(.print-sheet)`). It is not print rules over the drawer: printing the drawer produced a rounded card on a blurred backdrop with the servings +/- buttons on paper, and taming that with `print:` utilities means any restyle of the drawer silently changes what comes out of the printer. The sheet derives its ingredients from the same `displayIngredients` array the table renders, so a scaled or translated recipe prints what is on screen. `usePrintTitle` renames `document.title` during printing because browsers use it as the default PDF filename. **Consequence for tests:** while a recipe is open its text appears twice in the DOM, so `getByText` on recipe content must be scoped (e.g. `getByRole('dialog')`).
- **Public share links are opt-in and revocable, and the token is the secret.** `recipes.public_share_token` (migration 0061) is null until the owner creates a link and null again when they revoke it. An anonymous visitor reads through `get_shared_recipe(token)` — a `security definer` function with a pinned `search_path`. **What keeps `anon` out of the tables is RLS, not a missing grant**: Supabase grants `anon` SELECT on public tables as standard, and every policy on `recipes`, `recipe_images` and `recipe_translations` is `to authenticated`, so none applies to anon and row-level security denies by default. A pgTAP case asserting a `42501` permission error instead of zero rows is testing a hand-built fixture rather than the product, and will fail in CI. The recipe id is deliberately not the key: ids are not secrets anywhere else in this app (they sit in URLs, logs and the admin panel), so keying a public read on the id would make every recipe world-readable with no opt-in and no way back. The function **names its columns**: `select *` would have handed a public page the owner's `notes`, plus `user_id`, `rating` and the 768-float `embedding`, so a column added to `recipes` is private here until someone adds it to that list on purpose. `get_shared_recipe_images` and `get_shared_recipe_translations` (0063) follow the same three rules. A null token must never match a row, or revoking one recipe would publish every unshared one — covered by six pgTAP cases and by `tests/unit/publicShareLink.test.ts`.
- **The public pages render before `AuthGate`, so they must not assume a session.** `/r/:token` and `/about` make no table reads, and `useDarkMode` is called from `Layout` and `AuthGate` only — neither of which those routes render. `ThemeSync` exists solely to mount that hook on the three screens that render neither (share page, dead-link page, `/about`); without it every `dark:` class on them is dead and they stay light on a device set to dark. The guest page also has no path to any `/api` route: AI endpoints require a Bearer token and are rate-limited per user, so a guest may read a cached translation but can never cause one to be made.
- **A translation lives in three places, and deleting it must clear all three.** The row in `recipe_translations`; the list of stored languages in `useRecipeTranslations` (the picker's ticks); and the copy in `useTranslationCache` at `App` level, which `RecipeDetail` prefers over asking the server. Deleting used to clear the first two only. So the tick went, a confirmation appeared, and choosing the language again showed **the translation that had just been deleted** — no call to `/api/translate`, no new translation until a reload. That defeats the only reason to delete one: it came out badly and should be redone. `useTranslationCache` now exposes `forgetTranslation()`, wired to `RecipeDetail` as `onTranslationRemoved`. `tests/e2e/translationManager.spec.ts` translates, deletes and translates again against a table that behaves like one, and requires a second call; it fails with the forget removed. **Deleting is in the `⋯` menu, one entry per stored language, not on the language chips**: it is rare, and a cross on every translated chip made the picker read as a list of things to remove. - **Translation is gated on read visibility, not ownership.** `api/translate.ts` uses `userCanReadRecipe()`, which widens to linked accounts via `getVisibleUserIds()`. It lives in `extract.ts` because the Hobby plan's function limit leaves one slot. Two things are deliberate. **The model is told to return an empty recipe rather than invent one**, which fails `extractedRecipeSchema` by design — so that branch uses `safeParse` and answers **422** with wording of our own, instead of letting the `ZodError` handler return "Too small: expected string to have >=1 characters" as a 400. And **over-long text is refused, never cut** (`MAX_EXTRACT_TEXT`): a silent cut drops the end of the method, and a recipe missing its last steps looks complete. `RecipeForm` mirrors the two limits as plain numbers because `src` does not import from `api`; the schema is what enforces them. The form keeps the pasted text after a failure. With four import tabs the word "From" is hidden below `sm` and the icons below 360px — `tests/e2e/pasteRecipe.spec.ts` holds that all four fit at 320px and 390px.
- **Filter chips are applied in one place.** `applyTagFilter()` in `recipeStore.ts` is shared by `fetchRecipes` and `loadMore`, which previously held separate copies: a chip added to one and not the other filters the first page and then loads an unfiltered second page on scroll. Most chips are tags; `⭐ Favourites` and `🔗 Shared` are row properties.

- **Claude is the main provider; Gemini is the backup (migration 0069).** Chosen because the admin's Claude Max plan carries monthly API credit, and because much of `gemini.ts` exists to work around Gemini (per-family reasoning settings, aliases that moved, an id Google never served, 503s, a project block). `MODEL_OPTIONS` offers Claude Haiku / Sonnet / Opus 5.5 (`claude-haiku-5-5`, `claude-sonnet-5-5`, `claude-opus-5-5` — exact ids from Anthropic's model list; a guessed id would fail every call and the fallback would hide it) and the three Gemini tiers. 0069 sets the global row: **Opus** for `photo`; **Sonnet** for extract, translate, nutrition and as the main model; **Haiku** for tag, suggest, scale, shopping. **`photo` is its own task** (camera photos of cookbook pages and handwritten cards, the hardest reading job), separate from `extract` (web pages, PDFs, pasted text and **screenshots**, which carry clean digital text). The browser decides, because the upload re-encodes every image as JPEG and the server cannot tell afterwards. **The file format alone is not enough**: since iOS 26 an HDR screenshot is a HEIF, like a camera photo, and the file input (JPEG/PNG/WebP only) makes iOS hand either over as a JPEG. `imageKind()` in `src/lib/imageKind.ts` therefore decides, in order: (1) **camera EXIF** (exposure time, aperture, ISO, focal length — every camera photo has them, no screenshot does) → photo; (2) PNG/WebP/GIF → screenshot; (3) **a phone screen's shape** (long side / short side 1.95–2.35, i.e. 18:9 to 21:9; camera frames are 4:3, 3:2, 16:9), for screenshots whose metadata was stripped → screenshot; (4) device EXIF (Make/Model/Software) with no camera data → screenshot; (5) anything else → photo, the harder case, so a misjudged screenshot only costs Opus's extra time. EXIF comes from exifr's lite build (JPEG + HEIF), dynamically imported, so it is a separate ~15 KB gzipped chunk loaded only on a photo import; `src/exifr-lite.d.ts` declares that entry. Whether iOS keeps EXIF when it converts a HEIF to JPEG for the file input was not verifiable here — rule 3 is what covers it if not. The request carries `kind`; a client that sends none is treated as photos. Logged as `extract-photo` or `extract-screenshot`, and `taskForEndpoint` maps them to `photo` and `extract`. `api/extractPhoto.test.ts`, `src/lib/imageKind.test.ts` (which reads EXIF from three tiny real JPEGs embedded as base64). Five rules in `api/_lib/claude.ts`, each from the API reference: (1) **no temperature** — Haiku 5.5 rejects any sampling parameter; (2) **"reasoning off" is `output_config.effort: 'low'`** — Sonnet 5.5 rejects `thinking: disabled`, Opus 5.5 cannot switch thinking off at all, low effort is the one setting all three accept, and the log row records `thinking = 'low'`; (3) **answers are constrained by `output_config.format`**, converted from the same Gemini schemas in `responseSchemas.ts` (objects closed with `additionalProperties: false`, `nullable` as `anyOf` with null), so there is still one definition per answer — the Anthropic SDK's Zod helper was not used because some Zod schemas *transform* the answer (translation joins its steps) and the model must be asked for the pre-transform shape; (4) **bare-list answers are wrapped** in `{ result }` and unwrapped on the way back; (5) **a refusal or `max_tokens` stop is an error**, never an answer. The SDK's own retries are off (`maxRetries: 0`) so `callWithRetry` counts attempts and keeps the deadline; 408 and 529 joined the transient set. **Any Claude failure falls back to Gemini** (`shouldFallBack`), not just "cannot serve": the other provider is independent, so a missing or exhausted key, an outage, or a request Claude rejects all end on Gemini after one fast failure — which is also what makes deploying before the key exists safe. Haiku falls back to Gemini Lite, Sonnet and Opus to Gemini Standard. `describeGeminiError` maps Anthropic's 402 (out of credit) and 529 too, and never passes on a message carrying a provider status code: the SDK writes `"400 {...}"`, which the old brace check would have shown a cook. - **Recipes can be sent from the iPhone's Photos app, through an Apple Shortcut (migration 0070).** Safari does not support the Web Share Target API (WebKit bug 194593, open since 2019), so a web app cannot sit in the iPhone share sheet; a Shortcut can. It base64-encodes the selected pictures and POSTs `{ images, mode }` to `/api/extract?via=shortcut` with `X-Speisekammer-Key` — a branch in `extract.ts`, not a new function (Hobby limit). **Keys**: `spk_` + 32 random bytes, shown once, stored only as SHA-256 in `shortcut_keys`, which has RLS on and no policy (service key only, not even the owner can read the hash); made, replaced and revoked through `api/account.ts`. **Saved straight away, announced later**: `mode` `single` (default) reads all pictures as one recipe, `each` makes one recipe per picture; each recipe is read with `extractRecipeFromImages`, saved with its pictures as the gallery (first is the cover), then tagged and estimated with `enrich.ts` (their failure does not undo the import), and gets a `recipe_imports` row: `processing` → `saved` (with `recipe_id`, cascade-deleted with the recipe) or `failed` (with a reason worded for a person: "No recipe could be read from this picture." for a ZodError, the allowance message for `DailyLimitError`, else `describeGeminiError`). Owners read their rows and may set `seen_at` only (column grant; pgTAP covers it). **Shortcuts gives up after roughly 30 seconds** (no official figure; a developer-forum report), and reading several pages on Opus can take longer, so the answer comes within `REPLY_WITHIN_MS` (20 s): "Saved: <title>" if done, else 202 "Got it…" and the work finishes under `waitUntil` from `@vercel/functions`. Every answer is `{ message }`, shown verbatim as the notification. **Input is accepted however Shortcuts serialises it**: a JSON array, `{data}` objects, or one string with an image per line — even with each image wrapped every 76 characters, rejoined by recognising how each format's base64 begins (`splitBase64Images`); the format is sniffed from the bytes, HEIC is refused with "add Convert Image to JPEG". Photo vs screenshot uses the browser's rules (`shared/imageKind.ts`) on the originals, with exifr in Node and `imageSize()` from the bytes. **In the app** `useRecipeImports` drives `ImportBanner`, the amber **New** badge (`RecipeCard isNew`) and the `NEW_FROM_PHOTOS` chip, which filters by id through `recipeStore.newImportIds`; opening a recipe (`openRecipe` in `App`) marks its import seen. Covered by `api/shortcutImport.test.ts`, `api/accountShortcutKey.test.ts` (including that revoking a key never reaches account deletion), `api/_lib/imageBytes.test.ts`, `tests/e2e/shortcutImports.spec.ts` and seven pgTAP cases. **Sharing the Shortcut (migration 0071):** the admin builds it once, adds an *import question* for the key header (Apple clears a field that has one when the Shortcut is shared, so the admin's key never travels), shares it with *Copy iCloud Link* and pastes the link into Settings → iPhone Shortcut. It is stored as `settings.shortcut_url` on the global row (readable by everyone, writable only through admin `POST /api/account?action=shortcut-url`), and every user then gets an **Add to Shortcuts** button; the build steps stay as a folded fallback. Because every user's button opens it, the server accepts only `https://(www.)icloud.com/shortcuts/<id>` (`SHORTCUT_URL_PATTERN`) — not a CHECK constraint, which this table must not get. `api/accountShortcutLink.test.ts`, two pgTAP cases, and the last three cases of `shortcutImports.spec.ts`. The Shortcut itself is built by hand from the steps in `ShortcutSettings`; **it has not been run against a real iPhone from this repository** — the action names follow Apple's Shortcuts app as documented, and the server tolerates the ways its JSON can come out.
- **Gemini model ids: all three tiers are pinned; no alias points at any of them.** The Gemini part of `MODEL_OPTIONS` is Lite (`gemini-3.5-flash-lite`), Standard (`gemini-4-hydrogen`) and Frontier (`gemini-4-carbon`). Lite was `gemini-flash-lite-latest` until migration 0065 — **an id Google does not serve at all**, absent from their model list, so every call on that tier failed. PR #43 moved Standard and Frontier onto Gemini 4 and left Lite on a Flash alias. **There is no Gemini 4 lite model to move to**: the family is hydrogen, argon, carbon and neon, and argon is a *reasoning* model (cheaper per turn than carbon, nothing like a flash-lite) — so the cheapest model Google still serves is a 3.x one. 0065 rewrites both `settings.gemini_model` and any entry in `settings.task_models`. Aliases track releases *within* a tier — `gemini-flash-latest` moved 3.7 → 3.8 with no code change — but they do **not** carry across a generation: Google shipped Gemini 4 as hydrogen/carbon/argon and left `gemini-flash-latest` on the 3.x Flash tier, which then went 503. So PR #23's claim that aliases remove the need for code changes holds only inside a generation. **Frontier has no free allowance at all** — a free-tier key gets `limit: 0 … Free Tier` on every call — so its description says it needs billing. Always verify an id against `generateContent`: `ListModels` advertises retired models *and* models the key cannot call. `generateJson()` records the response's `modelVersion` in `gemini_logs.model_version`, so the concrete model behind any id is recoverable; the logs UI and the admin breakdown show that, not the id that was requested, and `tests/unit/modelDefaults.test.ts` fails if the logging is removed.
- **Changing the default model:** `DEFAULT_MODEL` lives in `src/lib/constants.ts` and `api/_lib/supabase.ts`, and the two must match. Since 0068 only the global row's `gemini_model` runs, so a change needs a migration doing `update public.settings set gemini_model = '<new>' where id = 1` (and, if the admin should not keep a task on the old model, its `task_models`). `tests/unit/modelDefaults.test.ts` enforces both — it fails if the two constants disagree, or if the newest migration assigning `gemini_model` does not name the current default. Verify a candidate id (alias or pinned) actually serves `generateContent` before shipping it: `ListModels` still advertises retired models (see migration 0044).
- **Vercel function limit:** Hobby plan allows 12 serverless functions. Currently 11 are in use (`share-preview.ts` was the 11th). `api/sharePreview.test.ts` fails if the directory ever holds more than 12. Do not add new `api/*.ts` files beyond 12 without upgrading the plan or merging endpoints.
- **The service worker must never register in development.** `registerServiceWorker()` returns early unless `import.meta.env.PROD`. vite-plugin-pwa's inline snippet only shipped in built output; moving registration into `main.tsx` turned it on for `npm run dev` too, which caches assets while you edit them and — because Playwright's `page.route()` does not intercept requests made through a service worker — silently broke the entire E2E suite. Every screen failed with empty data, a symptom that looks nothing like the cause. `playwright.config.ts` also sets `serviceWorkers: 'block'` as a second line of defence, and `E2E_PORT` / `E2E_MODE` exist so a local run cannot silently attach to another project's dev server on 5173.
- **A view that cannot load gets one reload, then a message. Never a loop, never a white page.** `recoverFromStaleChunks()` (`src/lib/recoverFromStaleChunks.ts`, wired in `main.tsx` before anything lazy-loads) reloads **once** when a code-split chunk fails to load. `App.tsx` lazy-loads twelve views and Vite fingerprints every chunk, so a deploy renames them; a browser holding an older `index.html` — which is what a service worker does — then asks for files that are gone, and `vercel.json`'s catch-all answers a missing `/assets/*.js` with `index.html` and a 200, so the import fails on the MIME type. **The reload must not re-arm itself.** The first version cleared its marker on the window `load` event, taking "the page loaded" for "the retry worked" — but `load` fires before a lazy chunk is even requested, so on a chunk that could never load every reload re-armed the next: **352 reloads in 20 seconds**, measured in a real browser against two builds and a real service worker, which a person sees as a page that flickers and cannot be used. That fix had replaced a white page, so it turned a dead screen into a strobing one. The marker is now a timestamp in `sessionStorage` that expires only with time (`RECOVERY_WINDOW_MS`); nothing that happens during a page load can reset it, and unavailable storage means no reload at all. When the reload does not help, the failed import reaches the top-level `ErrorBoundary` in `main.tsx` and `LoadFailure` says so, **names the file**, and offers a reload or a manual service worker reset — the lazy views sat under no boundary before, which is why the original symptom was blank. The `vite:preloadError` handler deliberately does **not** `preventDefault()`: that makes Vite resolve the import with `undefined` and the file name is lost. An automatic service worker reset as a second step was built and removed, because the case it was for could not be reproduced. Guarded by `src/lib/recoverFromStaleChunks.test.ts` (including the `load`-event regression, checked against the old behaviour put back) and `tests/e2e/loadFailure.spec.ts`. To reproduce the real thing: build twice with a string changed in between, serve with a static server that rewrites misses to `index.html`, and count `framenavigated` events.
- **PWA update path:** `vite-plugin-pwa` + Workbox precaching is configured in `vite.config.ts`, but registration lives in `src/lib/registerServiceWorker.ts` (`injectRegister: null`). Three things are load-bearing and each was a separate reason phones kept rendering an old build: `updateViaCache: 'none'` (or the browser compares the new worker against a copy from its own HTTP cache for up to 24h), an update check on `visibilitychange` (an installed PWA resumed from the app switcher never fires `load` again), and a one-shot reload on `controllerchange` guarded by whether a controller existed at start (`clientsClaim()` hands the open page over, but that page keeps the JS it already parsed; reloading unguarded would bounce every first-time visitor). `vercel.json` must keep `/sw.js` and `/index.html` on `max-age=0, must-revalidate` — hashed assets under `/assets/` stay immutable. Guarded by `src/lib/registerServiceWorker.test.ts`.
